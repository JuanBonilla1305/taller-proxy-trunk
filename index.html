Taller Proxy en el Trunk
Taller práctico · Patrones de diseño

Un Proxy para migrar sin salir de main

Van a cambiar cómo se calcula el envío de una tienda usando Trunk-Based Development. No hay ramas largas: cada paso es un commit pequeño que deja main en verde. El código nuevo entra apagado, detrás de un Proxy.

Duración 90 minModalidad parejasLenguaje Java 17 + JUnit 5Entrega URL del repositorio
Qué vamos a construir

La estructura final

El cliente (Checkout) solo conoce la interfaz. El Proxy implementa esa misma interfaz y decide a quién delegar. Por eso el código nuevo puede estar en main desde el primer día sin que ningún usuario lo use.

Reglas

Cómo se trabaja hoy

  • Un repositorio por pareja, con una sola rama: main.
  • Cada paso es un commit, con el mensaje que aparece en el paso.
  • Antes de cada commit corren los tests. Si main queda en rojo, se arregla antes de seguir.
  • Commits pequeños y frecuentes. El docente revisará git log --oneline en cualquier momento.
  • Rotan el teclado en cada paso: uno escribe y el otro revisa.

PASO 0

Proyecto base

Creen el proyecto con estas clases. Así está la tienda hoy: Checkout crea directamente el calculador viejo, sin ninguna interfaz.

public record Order(String id, String customerId, String city,
                    double subtotal, double weightKg) {}

public class LegacyShippingCalculator {
    public double calculate(Order order) { return 10.0; }
}

public class Checkout {
    private final LegacyShippingCalculator calc = new LegacyShippingCalculator();
    public double total(Order o) { return o.subtotal() + calc.calculate(o); }
}

public class FeatureFlags {
    private final java.util.Set<String> enabled = new java.util.HashSet<>();
    public void enable(String name)  { enabled.add(name); }
    public void disable(String name) { enabled.remove(name); }
    public boolean isEnabled(String name) { return enabled.contains(name); }
}
git commit -m "chore: initial shop with legacy shipping"
PASO 1

Extraer la abstracción

Creen la interfaz y hagan que el calculador viejo la implemente. El comportamiento no cambia.

public interface ShippingCalculator {
    double calculate(Order order);
}

public class LegacyShippingCalculator implements ShippingCalculator {
    @Override
    public double calculate(Order order) { return 10.0; }
}
git commit -m "refactor: extract ShippingCalculator interface"
PASO 2

El cliente depende de la interfaz

Checkout deja de crear su calculador y lo recibe por constructor.

public class Checkout {
    private final ShippingCalculator calc;

    public Checkout(ShippingCalculator calc) { this.calc = calc; }

    public double total(Order o) { return o.subtotal() + calc.calculate(o); }
}
git commit -m "refactor: inject ShippingCalculator into Checkout"
PASO 3

Crear el Proxy con el flag apagado

El Proxy implementa la misma interfaz y guarda una referencia a cada implementación. Mientras el flag esté apagado, el sistema se comporta igual que antes.

public class ShippingCalculatorProxy implements ShippingCalculator {
    private final ShippingCalculator legacy;
    private final ShippingCalculator smart;
    private final FeatureFlags flags;

    public ShippingCalculatorProxy(ShippingCalculator legacy,
                                   ShippingCalculator smart,
                                   FeatureFlags flags) {
        this.legacy = legacy;
        this.smart = smart;
        this.flags = flags;
    }

    @Override
    public double calculate(Order order) {
        return flags.isEnabled("smart-shipping")
                ? smart.calculate(order)
                : legacy.calculate(order);
    }
}

Mientras SmartShippingCalculator no exista, pueden pasar un stub temporal: order -> 0.0. Compila, los tests pasan y nadie lo usa porque el flag está apagado.

git commit -m "feat: add ShippingCalculatorProxy (flag off)"
PASO 4

Construir el cálculo nuevo de forma incremental

Una regla de negocio por commit, cada una con su test. El flag sigue apagado.

  • Regla A: el envío cuesta 2,5 por kilo.
  • Regla B: fuera de Bogotá se suman 5.
public class SmartShippingCalculator implements ShippingCalculator {
    @Override
    public double calculate(Order o) {
        double base = o.weightKg() * 2.5;
        return o.city().equals("Bogotá") ? base : base + 5;
    }
}
git commit -m "feat: smart shipping by weight"
git commit -m "feat: smart shipping surcharge outside Bogotá"
PASO 5

Ampliar el Proxy

Elijan una de estas extensiones. Todas mantienen la misma interfaz: el cliente no se entera.

LoggingRegistrar qué implementación respondió y cuántos milisegundos tardó.
CachéGuardar el resultado por order.id() y no recalcular.
CanaryUsar smart solo si Math.abs(customerId.hashCode()) % 100 < 20.
git commit -m "feat: proxy <logging|cache|canary>"
PASO 6

Encender y limpiar

Enciendan el flag, verifiquen que todo pasa y luego borren el código viejo. Un flag que nunca se borra se vuelve deuda técnica.

git commit -m "chore: enable smart-shipping"
git commit -m "chore: remove legacy shipping and flag"
Tests mínimos

Lo que debe pasar siempre

class ShippingCalculatorProxyTest {
    Order order = new Order("o1", "c1", "Medellín", 100, 4);
    FeatureFlags flags = new FeatureFlags();
    ShippingCalculatorProxy proxy = new ShippingCalculatorProxy(
            new LegacyShippingCalculator(), new SmartShippingCalculator(), flags);

    @Test void usaLegacyConFlagApagado() {
        assertEquals(10.0, proxy.calculate(order));
    }

    @Test void usaSmartConFlagEncendido() {
        flags.enable("smart-shipping");
        assertEquals(15.0, proxy.calculate(order)); // 4 kg × 2,5 + 5
    }

    @Test void checkoutFuncionaConCualquierCalculador() {
        Checkout checkout = new Checkout(o -> 7.0);
        assertEquals(107.0, checkout.total(order));
    }
}
